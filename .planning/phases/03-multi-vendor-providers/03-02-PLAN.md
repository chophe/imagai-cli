<objective>
Ship the one named non-OpenAI-compatible adapter the phase promises: a `fal` format whose request and response keys are genuinely its own, wired into the shared pipeline so the save, history and gallery paths are reused unchanged.

**As a** user of `imagai`, **I want to** configure named non-OpenAI-compatible providers alongside existing engines and select them per request, **so that** I can point at a vendor whose API is not OpenAI-shaped without waiting for the project to add it (ROADMAP Phase 3 **Goal:**, verbatim).

The chosen vendor is **fal.ai**, which satisfies D-36's "differ in BOTH request and response keys" test and D-39's "the seam is what video will reuse" intent: one endpoint family (`POST {base}/{model_id}`) serves image and video models alike, so a v2 video adapter is a new format name against the same registry rather than a restructuring. Its wire shape, verified against fal's published documentation while planning:

- Endpoint `POST https://fal.run/fal-ai/flux/schnell` — the model id **is** the path, so the body has no `model` key at all.
- Auth header `Authorization: Key <api_key>` — not `Bearer`.
- Request body keys `prompt`, `num_images`, `image_size`, `output_format` (`jpeg`|`png`), plus model-specific fields. There is no `n`, no `size`, no `response_format`, no `quality`, no `style`.
- Response `{"images": [{"url": "...", "content_type": "image/jpeg"}], "prompt": "...", "seed": ..., "timings": {...}, "has_nsfw_concepts": [...]}` — no `data`, no `b64_json`, no top-level `url`.
- Errors: a flat `{"detail": "Request timed out", "error_type": "request_timeout"}` for infrastructure failures, and a `{"detail": [{"loc": [...], "msg": "...", "type": "..."}]}` array for model validation failures. Neither is OpenAI's `{"error": {"message": ..., "type": ...}}`.

Purpose: D-25 locks exactly one adapter so the seam is proven end-to-end rather than half-covered; D-27 locks that the adapter maps onto the existing response shape so no second save path exists. Plans 03-03, 03-04 and 03-05 surface this engine and prove no regression.
Output: the `fal` adapter in `src/provider.rs`, the fal DTOs in `src/models.rs`, a fal mock mode in `tests/common/mod.rs`, and end-to-end coverage in `tests/core.rs`.

</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator env (`FORMAT`, `BASE_URL`, `MODEL`) → outbound URL | The fal endpoint is built by joining the configured base URL to the model id, so a model id containing a scheme or a `..` segment changes where the request — and the API key — is sent |
| fal HTTP response → `ImageGenerationResponse` | A remote JSON body is parsed into structs and its `url` is later fetched by `save_image_from_url`, so a hostile or broken body must never be trusted, half-parsed, or treated as a success |
| fal error body → user-visible message | The mapped message reaches stderr and the web API, so its content is an information-disclosure surface as well as a diagnostic |
| `extra_params` → request body | Operator-supplied JSON is merged into the outbound body verbatim, per D-31's escape hatch |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-03-04 | Spoofing | `src/provider.rs::fal_generate` — the request goes out with the wrong auth scheme, so the provider rejects it or, worse, an unauthenticated request reaches a logging intermediary | high | mitigate | The adapter sets `Authorization: Key {api_key}` explicitly rather than reusing `bearer_auth`, because fal documents `Key`; `tests/common/mod.rs` captures the header per path and `fal_engine_saves_image_through_the_shared_pipeline` asserts the sent value, so a regression to a bearer token fails the suite. `--verbose` dumps the body and URL only and never the header |
