<objective>
Carry the declared format through the web surface: one new field on `GET /api/engines`, and the format rendered in the three existing engine pickers of the single-page UI. No new route, no new picker, no selection change.

**As a** user of `imagai`, **I want to** configure named non-OpenAI-compatible providers alongside existing engines and select them per request, **so that** I can point at a vendor whose API is not OpenAI-shaped without waiting for the project to add it (ROADMAP Phase 3 **Goal:**, verbatim).

Purpose: D-33 makes success criterion 4 (all three surfaces) true by construction — the web `engine` field already carries a name and only the adapter behind it changes — so this plan adds no picker logic. D-34 caps the SPA work at rendering the format in the existing engine lists: the `engine`, `edit_engine` and `history_engine` selects are fed by one `loadEngines` function, so the change is one label template applied where the three option lists are built. Plan 03-05 then drives a real fal generation through `POST /api/generate`.

Output: the `format` field on `/api/engines`, the SPA option labels carrying it, and the tests that pin both.

</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator config → `GET /api/engines` JSON → SPA | Engine names, models, base URLs and now format labels cross from operator configuration into an unauthenticated, CORS-open JSON response and then into DOM construction |
| `GET /api/engines` → any client | The route is open with no authentication, so every field it emits is readable by anything that can reach the port |
| engine option label → DOM | The label string is assembled from configuration-derived values and inserted into the page |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-12 | Elevation of Privilege | `web_interface.html::loadEngines` — an engine name or format value containing markup reaches the page through an HTML sink | medium | mitigate | The option labels are built with `option.textContent`, which the existing code already uses and this plan requires be kept; the verify gate fails if an `innerHTML` sink appears on the label path. No engine value is ever placed in an attribute either |
| T-03-13 | Information Disclosure | `src/web.rs::list_engines` — the response exposes per-engine configuration to any client that can reach the unauthenticated server | low | accept | The added `format` field discloses only a member of a two-value closed set, and the route already exposes engine names, models and base URLs. INTEGRATIONS.md already documents this server as localhost-only with CORS wide open; this plan adds no new class of data and no new route |
| T-03-14 | Tampering | `src/web.rs::list_engines` — a second, web-specific format source drifts from the registry, so the JSON column disagrees with the CLI column and the TUI column | low | mitigate | `list_engines` calls the single `crate::formats::format_label` helper, and `engines_endpoint` asserts the JSON value for both an undeclared and a declared engine; no resolved/declared pair or web-only derivation exists |
| T-03-SC | Tampering | npm/pip/cargo installs | high | accept | No package-manager install in this plan: no dependency change, no CDN asset added to the SPA. `axum`, `serde_json` and `tower` are already dependencies audited by the Phase 1 supply-chain gate |
