<objective>
Introduce the declared wire format: a new per-engine env field `IMAGAI__ENGINES__<NAME>__FORMAT` with a closed set of names, and the registry (`src/formats.rs`) that resolves a declared format ahead of any inference and states whether that format can accept image input.

**As a** user of `imagai`, **I want to** configure named non-OpenAI-compatible providers alongside existing engines and select them per request, **so that** I can point at a vendor whose API is not OpenAI-shaped without waiting for the project to add it (ROADMAP Phase 3 **Goal:**, verbatim).

This plan is the seam, not a provider. It changes what an engine *declares*, not what any existing engine *does*: with no FORMAT set, every existing engine resolves to the OpenAI-compatible family and takes the code path it takes today (D-28). Two decisions land here: D-24 (config-only declared format, closed name set, no new dependency) and the capability half of D-30 (`edit_transport` becomes format-driven, still failing before any socket opens and naming engine+model per D-05). The one named non-OpenAI adapter itself is Plan 03-02.

Purpose: D-24 rejected both inferring the format from `base_url` (today's unreliable sniffing) and a Rust trait registered in code (a code change per provider); D-29 fixes the precedence rule that makes a declaration meaningful. Without this plan, a second adapter would have to be wired by hand for every engine.
Output: `src/formats.rs`, the `format` field on `EngineConfig` plus its env parsing, the format-driven capability gate in `edit_transport`, and the mechanical field churn across existing test literals.

</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator env (`IMAGAI__ENGINES__<NAME>__FORMAT`) → request routing | A declared format is operator-supplied configuration that selects which adapter builds the body; a typo or an unrecognised value would silently misroute a paid request to the wrong family |
| engine config → edit capability decision | `edit_transport` decides whether an engine may take image input; deciding wrongly either wastes credits on a request the provider rejects or refuses a request the engine could serve |
| engine config → displayed format label | `list-engines`, the TUI and `/api/engines` all derive their column from the same declared value, so a label that misrepresents the format steers the operator to the wrong engine |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Tampering | `src/config.rs::Settings::load` — an unrecognised `FORMAT` value silently falling back to the OpenAI-compatible family | medium | mitigate | The closed set in `ProviderFormat::from_declared` rejects anything but `openai` and `fal`; `resolve` turns that rejection into a hard error naming the engine and the supported names, and `Settings::load` prints a `[warning]` at load time so the typo surfaces before a prompt is typed. No code path maps an unknown value onto a working format |
| T-03-02 | Denial of Service | `src/provider.rs::edit_transport` — an engine refused for the wrong reason, or a capability decision made after a socket opens | medium | mitigate | `resolve` runs first and is pure (no I/O); the capability check is a single `supports_image_input` call before any HTTP client is built. `edit_against_fal_format_fails_before_any_request` asserts the mock records zero requests, which is the executable proof that nothing left the machine |
| T-03-03 | Spoofing | `src/formats.rs::format_label` — a label that shows a resolved default for an engine whose declaration is broken, hiding the misconfiguration from `list-engines` | low | mitigate | `format_label` returns the declared value verbatim when `from_declared` rejects it, and the resolved name otherwise; the unit tests pin all three branches. The one display helper is shared by every surface so the CLI, TUI and web columns cannot disagree |
| T-03-SC | Tampering | npm/pip/cargo installs | high | accept | No package-manager install in this plan: `Cargo.toml` is untouched, which is itself D-24's "config-only, no new dependency". The crate's existing dependencies are already in the lockfile and audited by the Phase 1 supply-chain gate |

</threat_model>
