<objective>
Create the project's first persistence layer: a single JSON sidecar `.imagai-history.json` inside `output_dir`, and the hook on the shared pipeline that records a node for every image that lands there.

**As a** user of `imagai`, **I want to** view an image's iteration lineage and fork any past result into a new edit without losing the original, **so that** I can branch instead of starting over (ROADMAP Phase 2 **Goal:**, framed against PROJECT.md Core Value — "with the iteration history preserved so users can branch instead of starting over"; the Goal line is a capability sentence, so the `so that` half comes from Core Value verbatim rather than invented).

`src/history.rs` owns the record shape (`id`, `parent`, `filename`, `prompt`, `model`, `created`) and the sidecar read/write. `generate_image_core` records after each successful save, so CLI, TUI and web cannot drift on what is recorded — BRCH-04's "same history" starts here. A failed sidecar write is deliberately non-fatal: the image is real, and lazy adoption (D-10) recovers the node on the next read.

Purpose: D-08 locks the sidecar design (human-readable, no new dependency, survives restarts); D-09 defines root/child derivation; D-11 locks read-modify-write; D-20 and D-23 fix truthfulness and portability. Plans 02-02, 02-03 and 02-04 consume this API and run in parallel after it.

Output: `src/history.rs`, the recording hook in `src/core.rs`, the relocated `datetime_iso` helper, unit coverage in `src/history.rs`, and an end-to-end test in `tests/core.rs`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| sidecar file → history view | A hand-edited or corrupted `.imagai-history.json` enters `load_view` and every node's `filename` is later joined onto `output_dir` by the fork and step-back paths, so an injected `../` component would read and write outside the directory |
| record `parent` → tree shape | A record naming a parent id that does not exist could attach a subtree to nothing, or a cycle could make derivation loop |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Tampering | `src/history.rs::load_view` — injected separator in a record's `filename` | high | mitigate | Every consumer that turns a record `filename` into a path reduces it with `Path::new(f).file_name()` before joining under `output_dir`, exactly the reduction `output_dir_file` performs; a value that yields no usable final component is never joined. `load_view`'s unit tests include a record whose `filename` carries a parent-directory component and assert the derived view still resolves inside `output_dir` |
| T-02-02 | Tampering | `src/history.rs::load_view` — unknown or cyclic `parent` id in a hand-edited sidecar | medium | mitigate | Tree derivation drops any `parent` that names an unknown id, so such a record becomes a root; derivation is a single pass over a parent→children index rather than recursion over the records, so a cycle cannot loop |
| T-02-03 | Information Disclosure | the `Could not read history at {path}` sentence | low | accept | The path is the operator's own configured `output_dir` and the reason is a parse or I/O error string; no key, base URL, or path outside `output_dir` appears. The sentence is required by the Copywriting Contract because a silent empty tree would hide real lineage |
| T-02-04 | Denial of Service | whole-sidecar read-modify-write per save, unbounded growth | low | accept | D-11 accepts this cost for a single-user local tool and D-21 defers pruning; the sidecar is written once per saved image, not per request, and stays readable at gallery scale |

`T-02-01` and `T-02-02` are the two rows `/gsd-secure-phase` must re-audit against the shipped code.
</threat_model>
