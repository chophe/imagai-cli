<objective>
Put the lineage in the browser: a history view of every session tree and a fork button that starts an edit from the selected node, over the same sidecar and the same core the CLI and TUI use.

**As a** user of `imagai`, **I want to** view an image's iteration lineage and fork any past result into a new edit without losing the original, **so that** I can branch instead of starting over.

`GET /api/history` serializes the `history::HistoryView` that the CLI already serializes — one struct, one shape (D-19). `POST /api/fork` resolves its source through the same resolver the CLI and TUI use, builds the same `ImageGenerationRequest`, calls the same `generate_image_core`, and returns `result_items_json` unchanged so the two edit-family endpoints cannot drift apart. `is_plain_filename` governs every path-shaped field exactly as on `/api/edit`, because this is where an unauthenticated request crosses into the filesystem.

Purpose: BRCH-04 requires identical behaviour across surfaces, and the web surface is where an untrusted request crosses into the core. The new SPA markup is composed only from classes that already ship — `.form-grid`, `.form-group.full-width`, `.section-title`, `.help-text`, `.generate-btn`, `.output-content`, `.image-preview` — with no new CSS rule, no new dependency and no JS toolchain.

Output: `ForkPayload`, the two routes and handlers, the SPA history form with `loadHistory`/`executeFork`, and the `tests/web.rs` coverage.
</objective>

| Boundary | Description |

| T-02-11 | Denial of Service | unbounded reference count and a large history payload | medium | mitigate | The reference count above 16 is refused with both counts stated, before any read or network call. `GET /api/history` returns the whole tree because D-11 accepts gallery-scale cost for a single-user local tool; the browser sends filenames rather than image bytes, so the fork payload stays small and no upload endpoint is added |
