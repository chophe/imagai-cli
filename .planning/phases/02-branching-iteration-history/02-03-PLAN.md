<objective>
Give the TUI the same lineage the CLI has: a History tab that lists every session tree, shows the selected node's detail, and forks an edit from the selected node — plus a ` Pick from history… ` entry in the Edit tab's source picker.

**As a** user of `imagai`, **I want to** view an image's iteration lineage and fork any past result into a new edit without losing the original, **so that** I can branch instead of starting over.

`TABS` becomes `["Generate", "Edit", "History", "Engines", "About"]` with History at index 2, because fork always continues in the Edit tab. That index shift is this plan's main hazard: `draw`'s `match self.tab` (line 881) and `draw_footer`'s (line 1465) both need re-pointing, and the `_ => draw_about_tab` catch-all must become an explicit index-4 arm so a future tab cannot silently land on About. Tree scrolling reuses `PickerState`'s `selected`/`scroll`/`height` triple and `picker_move`; the picker overlay is not forked into a second type (UI-SPEC rule 3).

Purpose: BRCH-04 requires identical operations on all three surfaces. This plan is the TUI half — the tree is ratatui `Line`/`Span` rows (UI-SPEC: no new rendering technology), every failure routes through `push_log`, and no `unwrap` appears outside `#[cfg(test)]`.

Output: `HistoryState`, `draw_history_tab` + its detail pane, `handle_history_key`, the pick-from-history flow, and the TUI unit tests.
</objective>

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-02-08 | Elevation of Privilege | the re-indexed tab dispatch silently routing a future tab to the About renderer | low | mitigate | The `_ =>` catch-all in both `draw` and `draw_footer` is replaced by explicit arms over 0..=4, so an out-of-range index panics in development rather than rendering the wrong surface in production. `tabs_has_history_at_index_two` asserts exhaustiveness by exercising both dispatchers for every index |
