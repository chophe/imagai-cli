<objective>

`imagai edit --image <path> -p "<change>"` must reach the provider, come back, be saved into
the same flat `output_dir` the generation path already uses, and carry its source lineage in
the PNG — through clap routing, the shared request DTO, the application core, the provider
transport, and the shared save helpers. This plan also installs the engine capability gate
(D-05), the `-edit` filename scheme (D-06) and the PNG lineage record (D-07), then extends
the same path to multiple reference images (EDIT-03).

01-02), the web API (plan 01-03), the TUI tab (plan 01-04) — is a caller in front of the
capability this plan makes real. Building it first means those plans add entry points, not
new plumbing.

`src/provider.rs`, `source_image`/`ref_images` on `ImageGenerationRequest`, `-edit` filename

</objective>

<assumption_delta_decision>
**Detector result:** `detected: true` — one `pluralization` signal, term `multiple`, from
ROADMAP success criterion 3 ("User can pass multiple reference images to a single edit request").

**Question it raises:** the edit request previously carried exactly one image — or none. One
image has become a source plus N references. Does the identity model still name the right noun?

**Noun that is primary:** the **source image**. Not "the images", not "the inputs" — the source.
`ImageGenerationRequest.source_image` stays singular and is the thing everything else keys off:
the output filename stem comes from it, and the PNG `Source` lineage records it.

**Decision:** `add-alongside`, with `ref_images: Vec<String>` as an adjunct list rather than
promoting the whole thing to a plural `sources: Vec<String>`.

**Rationale:** a promoted plural primary would make two locked decisions unanswerable. D-06
derives the output filename from the source stem — "which stem names `<stem>-edit.<ext>`?" has no
answer once there are several equally-primary sources. D-07 records a single `Source` value in the
PNG — one lineage field cannot point at three files. Promoting would force D-06 and D-07 to be
redesigned in the same commit, which is exactly the trade this decision exists to avoid.

**Where the generalization already happens, deliberately:** at the transport boundary the two are
indistinguishable. `generate_edits` builds one ordered path list — source first, then refs — and
emits an identical `image[]` part per entry; the chat-vision path does the same with `image_url`
content parts. A wire format that treats N sources as equals needs no change below this line. So
the pluralization is contained at the identity layer and expressed at the wire layer, which is
the boundary where it is cheap.

**Accepted debt, and what would force the later promote:** if Phase 2's iteration history tree
needs several parent images per node (a genuine multi-source composite rather than a
source-plus-references blend), the plural must be promoted and `Source` becomes a list. The
signal to watch for is a Phase 2 decision that a history node can have more than one parent.

**Companion invariant test (suggested, not required):** "every supported transport variant
receives the source as its first image" — encoded by `edit_sends_multiple_reference_images_in_order`
in Task 3 and by the `messages[0].content` index assertions in
`edit_via_openrouter_chat_sends_data_uri_parts`.
</assumption_delta_decision>
