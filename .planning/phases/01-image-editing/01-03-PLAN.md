<objective>
Put the edit flow on the second of the three surfaces, with the same capability gate and the
same saved output as the CLI.

`POST /api/edit` takes a prompt, an optional engine, a source filename, reference filenames
and an output filename; the handler reduces every path-shaped field to its final component
before joining it under `output_dir`, builds the same `ImageGenerationRequest` the CLI builds,
and calls the same `generate_image_core`. The browser form gains an Edit section whose source
and reference pickers are populated from the existing `GET /api/images`.

Purpose: `PROJECT.md` records "Ship across all three surfaces" as a key decision, and
ROADMAP success criterion 4 requires the edit flow to be available on CLI, TUI and web with
equivalent results. The web surface is where an untrusted request crosses into the core, so it
also carries this phase's only real trust boundary — the filename guard and its traversal
tests live here.

Output: `EditPayload`, the `/api/edit` route and handler, the output_dir filename guard, the
browser edit form, and the `tests/web.rs` coverage for the endpoint, the guard, multi-reference
and the capability gate.
</objective>

Path traversal on the web edit payload is canon security — it is not minted here as a

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser request → web handler | JSON fields (`engine`, `source`, `refs`, `output`) arrive from an unauthenticated HTTP client on a server that binds `0.0.0.0` by default, then cross into filesystem reads, a network call to a provider, and a write under `output_dir` |

## STRIDE Threat Register
